# agentica-campfire

Group chat written in [Agentica](https://github.com/agentica-lang/agentica): a port of 37signals' [ONCE Campfire](https://github.com/basecamp/once-campfire), built on [Bond](https://github.com/agentica-lang/bond), EAG templates and [agentica-db](https://github.com/agentica-lang/agentica-db).

This is an independent project. It is not affiliated with or endorsed by 37signals. Campfire is MIT licensed (copyright 37signals, LLC). Any CSS, JavaScript or images reused from it keep that copyright and license notice, and the notice is added to this repository when the first file is copied.

Status: a skeleton with a database, sign-in, the join link, the people page, password reset by email, and rooms with plain-text messages. A Bond server on a SQLite database whose schema (accounts, users, sessions, password resets, rooms, memberships, messages, boosts, attachments, webhooks and the message search index) is created by numbered migrations at start-up. On the first run there is no account, so every page sends the visitor to a setup form that makes the first user, an administrator; after that people sign in with an email and a password, and sign out. The first run also makes the open room "All Talk". The home page and the rooms need a sign-in; `GET /health` does not. See [docs/plan.md](docs/plan.md) for what Agentica, Bond and agentica-db still need, the MVP and the phases.

## Run

Needs [Agentica](https://github.com/agentica-lang/agentica) 0.23.0 or later on `PATH`.

```sh
make install   # fetch Bond and agentica-db (pinned by commit in agentica.toml) into deps/
CAMPFIRE_SESSION_SECRET=$(openssl rand -hex 32) make run   # http://127.0.0.1:3000/
```

Open the address: the app has no account yet, so it shows the setup form (your name, an email and a password of at least 8 characters). That makes the administrator and signs you in. Whoever reaches `/first_run` first becomes the administrator, so do the setup before the app is reachable by anyone else: it listens on `127.0.0.1` by default, and `CAMPFIRE_HOST` should stay that way (or sit behind a firewall or a proxy that only you can reach) until the account exists.

`CAMPFIRE_SESSION_SECRET` is required, at least 32 bytes, and has no default: it signs the session cookie, so keep it out of the repository and the image, and use the same value on every start (a new one signs everybody out). Behind HTTPS set `CAMPFIRE_SECURE_COOKIES=true`, which makes the cookie `Secure` with the `__Host-` prefix (a browser then refuses it over plain HTTP). The cookie holds a random token that is checked against the `sessions` table, lasts 30 days and is `HttpOnly` with `SameSite=Lax`; signing out deletes the row, so a copy of the cookie stops working. Passwords are stored as scrypt digests (cost 2^16, block size 8, two lanes, a random salt each, in the form `scrypt$N$r$p$salt$key`) and never logged. At most two passwords are hashed at the same time (each takes about a second and 64 MiB); a sign-in or first-run form that arrives while both are busy is answered `503` with `Retry-After`. There is no per-IP rate limit yet (it needs the client address in Bond, [bond#46](https://github.com/agentica-lang/bond/issues/46)), and the hashing blocks a scheduler until [agentica#1049](https://github.com/agentica-lang/agentica/issues/1049). The first line of output says whether the cookie is `Secure`. Forms are protected against other sites with Bond's `Sec-Fetch-Site` and `Origin` check, with no token.

Rooms and messages (no live updates yet: a page shows what the database holds when it is asked for): the sidebar lists the rooms that a person is in, `New room` makes an open room, which puts every active person in it (any member may make one; the setting that restricts it to administrators comes later), and `/rooms/ID` shows the last 40 messages of a room, the newest at the bottom, with an `Older messages` link to the 40 before them (`?before=ID`, paged by message id) and a form that posts a plain-text message of at most 10000 characters. A message is stripped of the space around it, stored so and escaped in the page; there is no rich text, link or mention handling yet. The form carries a random `client_message_id`, so posting it twice (a double click, a retry) stores one message (the id is the key together with the person, so it must not be reused for another message, in any room). A person only sees a room they have a membership row in: a closed or direct room of other people, and a room that was never made, are the same `404 Not Found`, and a message posted to one is refused the same way before its text is looked at. `New closed room` makes a room with a member picker (checkboxes of the active people; the maker is always in it, and only the chosen people get a membership, in one transaction), and the maker of a closed room or an account administrator (who is in it, as upstream's `can_administer?`) can rename it and add or remove people on its settings page (`/rooms/ID/settings`); another member of the room is answered 403 there, and sees no Settings link, while a person who is not in the room still gets 404, checked first. The form never takes out the person who sends it. It carries the people who were in the room when the page was drawn (`was`) and saving applies only its own diff (the people it checked and `was` did not have are added, the ones in `was` it unchecked are taken out), so a stale form neither takes out someone added since nor brings back someone taken out since; a person who is not active stays in. The update checks again, inside its transaction, that the room is still closed and that the person may still change it, and rolls back otherwise. `New direct message` picks one or more people; the same people (the person included) open the direct message that exists instead of making a second one (the people are checked as active, the search and the insert run in one write transaction, so forms that arrive together make one room), and each person sees it named after the others. The settings of a room of another kind, and of a room of other people, answer the same 404, before the form is read. Leaving a room, making a room that only administrators may make, and removing yourself are for later.

The join link and the people: the account has a join code (made by the first run, `a1b2-c3d4-e5f6`), and `/join/CODE` is a form where a new person signs up with a name, an email and a password (of at least 8 characters); they become a member, join every open room that exists and are signed in. It is the only page besides the sign-in ones that needs no session. A code that is not the account's, an old one of a regenerated code included, answers the `404 Not Found` that a page that does not exist answers (and the form is not read), a form for an email that has an account (a deactivated person's too) is refused with a message (the join page tells that, but only to whoever has the link), and forms that arrive together with one email make one person: the code and the email are checked again inside the write transaction, after the password was hashed with the same limit of two hashes at a time (`503` with `Retry-After` past it, with the form again). The people page (`People` in the sidebar, at `/users`) lists the active people for everybody; an administrator also sees their emails and roles, the join link (it starts with `CAMPFIRE_BASE_URL` when that is set, and is only the path otherwise) with a button that makes a new one (the old link stops working at once), and a button to deactivate each person but themselves, or to reactivate a deactivated one. Deactivating ends the sessions of that person and keeps them from signing in (their messages and rooms stay); reactivating puts them in the open rooms that were made while they were away. Everything but the page answers `403` to a member who is not an administrator, `404` for a user that does not exist or is a bot, and the role is checked again inside the transaction. The pages that show the code are `no-store` with `Referrer-Policy: no-referrer`. The code is 48 random bits and there is no per-IP limit on the join page yet ([bond#46](https://github.com/agentica-lang/bond/issues/46)); regenerate the link when it is no longer wanted.

Password reset (needs email): "Forgot your password?" on the sign-in page asks for an email, and the answer is the same page whether or not an account has it, so it cannot be used to find out who is registered (the work behind it differs by a few queries, which a timing measurement could in principle tell apart). For an active account it emails a link, `BASE_URL/password_reset/edit?token=...`, with a random 256-bit token of which the table `password_resets` keeps only the SHA-256. The link works once and for 30 minutes, while a person has a link that works, asking again sends nothing (so a stranger cannot replace the link that the person is about to open), and after a link was used or made, a new one comes only five minutes later, so the form cannot be used to flood an inbox (until the per-IP limit of [bond#46](https://github.com/agentica-lang/bond/issues/46) there is no other limit). Requests that come together are decided inside one write transaction (`BEGIN IMMEDIATE`, which takes the write lock first), so they send one email, and two forms for one link change the password once (the second one may hash for nothing, which the limit on hashes bounds); a request that finds the database busy waits for it by sleeping in its task (agentica-db), so a burst does not fail with "database is locked", even with one or two schedulers. The wait is bounded by the `busy_timeout` of agentica-db (5 seconds by default); a request that waits longer gets a database error, which the app answers with `500`. Opening the link only shows the form (a mail scanner that opens it uses nothing up, and the page is `no-store` with `Referrer-Policy: no-referrer`); the post of the form sets the new password with the rules and the hashing limit of the first run (a post that finds the slots busy gets 503 with the form again), deletes every session of that person, uses the link up and signs the browser in. A `CAMPFIRE_BASE_URL` on `http://` for a host that is not this machine is warned about at start, and refused when `CAMPFIRE_SECURE_COOKIES` is true.

`CAMPFIRE_SMTP_URL` says how to send email (the password reset uses it): `smtp://user:password@host:587` (or `smtp+starttls://`) sends over STARTTLS and refuses to send unless the server offers it, `smtps://user:password@host:465` uses TLS from the first byte, and `smtp+plain://host:1025` uses no TLS and is only accepted for a host on this machine (a mail catcher in development). The user and the password are percent-encoded (`%40` for `@`), both are left out for a server without login, and the password is never logged or shown in an error. Unset means no email: the app says `mail: off` at start and has no password reset (its pages answer 404, and the sign-in page has no link to it). With the url set, `CAMPFIRE_BASE_URL` (`https://campfire.example.com`: a scheme, a host and maybe a port, no path) is required, since the links in emails start with it and the `Host` of a request is the visitor's to choose; `CAMPFIRE_SMTP_FROM` is the sender (`Campfire <campfire@HOST>`, for the host of the base url, by default) and `CAMPFIRE_SMTP_HOSTNAME` the name that EHLO says (that host by default; a base url with an IPv6 address needs both). Email is sent by a task (`src/mailer.agc`) that the app hands messages to, so a slow or dead mail server never holds up a page: the queue holds 32 messages (`CAMPFIRE_MAIL_QUEUE_SIZE`, 1 to 1024, ignored when email is off), a message that cannot be sent is logged with the code and the label of the refusal only (`campfire: mail: a message to 1 recipient was not sent: smtp 535: authentication failed`: no password, no address, no words of the server) and dropped (a reset link is deleted, so that the person can ask again, only when the message is dropped as it is queued, because the queue is full or the mailer has stopped; a message that fails to send, or that a stop gives up on, leaves its link alive until it expires after 30 minutes), and a stop of the app sends what is queued first (it waits up to 10 seconds, then logs how many it dropped). The code is `src/smtp.agc` (`Smtp.send(message, options)` for one message, `Smtp.connect`, `Smtp.send_message` and `Smtp.quit` for several on one connection) and `src/smtp_message.agc` (the message: headers, UTF-8 subject, text or text and HTML); they import nothing else of the app, so they can move to a package of their own.

`CAMPFIRE_HOST` and `CAMPFIRE_PORT` change where it listens (`CAMPFIRE_PORT=0` picks a free port, and the last line of output says which). `GET /health` answers `{"schema_version":11,"status":"ok"}`.

The app keeps its files in `CAMPFIRE_DATA_DIR` (`data/` by default, no `?` in it). Start-up makes the folder and the parents that are missing with mode 0700 (the database holds password digests and tokens, and SQLite makes the file with the umask), and leaves a folder that exists as it is. The database is `sqlite:DATA_DIR/campfire.db?fts5=required` unless `CAMPFIRE_DATABASE_URL` says another [agentica-db SQLite url](https://agentica-lang.github.io/agentica-db/guide/sqlite/) (WAL mode and foreign keys are on by default; add `fts5=required` to stop at start-up when the system SQLite has no FTS5, which message search needs). At start-up the app runs the migrations that the database has not seen (`src/migrations.agc`) and prints `database: schema version N, migrations applied: M`; if the database cannot be opened or migrated it exits with code 1 and a message that names the variable. Run one instance at a time per database: migrations run from one process, and two started together make one of them fail on `schema_migrations`. A url with `foreign_keys=off` is refused at start-up, since the schema relies on cascades. Back up with `VACUUM INTO`, or copy the file after the app stops: while it runs, recent writes may live in the `-wal` file.

## Develop

The tests are BDD first: `specs/auth.feature`, `specs/session_config.feature`, `specs/home.feature`, `specs/rooms.feature`, `specs/closed_rooms.feature`, `specs/direct_rooms.feature`, `specs/messages.feature`, `specs/join.feature`, `specs/join_link.feature`, `specs/users.feature` and `specs/database.feature` start the app on 127.0.0.1 and a free port, with a fresh database and a session secret of their own, and talk to it over HTTP with a small browser that keeps cookies (`specs/http_steps.agc`); `specs/password_reset.feature` and `specs/mail.feature` start the SMTP peer of `specs/fixtures/smtp_peer.agc` as the mail server, read the email that the app sends and follow its link; `specs/smtp.feature` runs the SMTP client against the same peer; `specs/schema.feature` checks the rules of the schema (foreign keys, unique values, the search index) through SQL steps; `test/` has unit tests of the config, the password hashing, the hashing limit and the layout. Hashing a password takes about a second at this cost, so the suite takes under a minute.

```sh
make check
make test
```

CI (`.github/workflows/ci.yml`) pins the Agentica release with its sha256.
